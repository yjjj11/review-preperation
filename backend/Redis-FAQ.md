## 基础概念篇

### 1. Redis 为什么这么快？单线程和多线程演进是什么样的？

**Q:** Redis 单机能达到 10万+ QPS，速度快的核心原因是什么？单线程为什么比多线程还快？Redis 6.0 多线程改了什么？

**A:**

Redis 单机读性能最高可达 11万次/秒，写性能可达 8万次/秒，远超传统关系型数据库。核心原因按重要性排序：

**1. 全内存存储**：所有数据都存在内存中，内存读写速度是磁盘的百万级，从根源上避免了磁盘 IO 的巨大开销，这是 Redis 快的最核心前提。

**2. 极致优化的数据结构**：Redis 核心数据结构都针对内存和性能做了特殊设计：
- 字符串用 SDS（简单动态字符串），O(1) 获取长度，二进制安全，比 C 原生字符串性能更高；
- 有序集合用跳表，查询和更新都是 O(logN)，实现简单，范围查询方便；
- 小数据用压缩列表，所有元素连续存储，省掉指针空间，极致节省内存；
- 列表用 quicklist（压缩列表+双端链表），兼顾空间和性能。

**3. 单线程执行核心命令**：Redis 的核心命令执行是单线程的，反而带来性能优势：
- 避免了多线程的上下文切换开销；
- 避免了多线程锁竞争、死锁等复杂问题；
- 不用处理线程同步，CPU 缓存命中率更高；
- **误区澄清**：这里的单线程仅指核心命令处理，Redis 的网络 IO、持久化、异步删除、集群同步都会开额外线程/进程。

**4. IO 多路复用模型**：Redis 使用 epoll/kqueue/evport 等 IO 多路复用技术，一个线程就能同时高效处理成千上万个客户端连接，避免了阻塞 IO 的性能瓶颈，充分利用网络带宽。

**5. C 语言开发**：更贴近操作系统，没有虚拟机、垃圾回收等额外开销，执行效率更高。

---

**Redis 单线程 vs 多线程演进：**

- **Redis 6.0 之前**：核心命令执行单线程，网络 IO、持久化用子进程/子线程处理；
- **Redis 6.0+**：引入**多线程 IO**，但**核心命令执行依然是单线程**：
  - 多线程仅用来处理网络请求的读写、协议解析；
  - 把耗时的网络 IO 操作分摊到多个线程，进一步提升并发处理能力；
  - 命令执行依然串行单线程，保证了原有原子性，不引入线程安全问题。

**一句话总结：** Redis 的快，核心不是多线程，而是 **全内存 + 单线程命令执行 + IO 多路复用** 的极致设计。

### 2. Redis 和 Memcached 区别？怎么选？

**Q:** Redis 和 Memcached 都是缓存，区别是什么？

**A:**

| 对比维度 | Memcached | Redis |
|----------|-----------|-------|
| **数据类型** | 只支持简单字符串 | 支持 String/List/Hash/Set/Zset 多种数据类型 |
| **持久化** | 不支持持久化，重启丢数据 | 支持 RDB/AOF 持久化，可以做数据持久化存储 |
| **线程模型** | 多线程，依赖锁机制 | 单线程（命令处理），无锁竞争 |
| **内存管理** | LRU 自动淘汰 | 多种淘汰策略，支持自定义过期时间 |
| **集群模式** | 支持分布式，但原生不好用 | 原生支持哨兵、集群，高可用方案成熟 |
| **适用场景** | 纯缓存、小数据简单缓存 | 缓存+持久化存储，复杂数据结构操作 |

**选择原则**：
- 简单缓存场景，数据可以丢 → 选 Memcached（多核扩展性好一点）
- 需要持久化、复杂数据结构、高可用 → 选 Redis（现在绝大多数场景都用 Redis）

### 3. Redis 有哪些数据类型？各自适用场景？

**Q:** Redis 支持哪几种数据类型？分别用在什么场景？

**A:**

| 数据类型 | 底层实现 | 适用场景 |
|----------|----------|----------|
| **String** | 简单动态字符串 SDS | 缓存对象、计数器、分布式 ID、session 存储 |
| **List** |  quicklist（压缩列表+双端链表） | 消息队列、最新消息列表（比如朋友圈最新动态）、栈/队列 |
| **Hash** | 压缩列表/哈希表 | 存储对象信息（比如用户信息），比多个 String 更省空间 |
| **Set** | 哈希字典 | 共同好友、标签去重、抽奖随机抽取、判断存在 |
| **ZSet** | 跳表 | 排行榜、延时队列、按分数排序、分页查询 |
| **Bitmap** | 字符串二进制位 | 用户签到统计、布隆过滤器、用户在线状态统计 |
| **HyperLogLog** | 基数统计 | 统计 UV 不精确去重，省空间 |
| **Geo** | 有序集合 | 地理位置计算、附近的人 |

### 4. Redis 的过期删除策略是什么？为什么用组合策略？

**Q:** 我们给 key 设置了过期时间，Redis 什么时候删除过期 key？用什么策略？

**A:**

过期删除策略解决的问题：key 过期后，何时删除以释放内存。Redis 默认使用 **惰性删除 + 定期删除** 组合策略。

**惰性删除：**
- 不会主动删除过期 key，只有当客户端访问这个 key 时，才检查是否过期，如果过期就立即删除，返回空。
- **优点**：CPU 友好，只有访问时才检查，不会浪费 CPU 资源；
- **缺点**：内存不友好，大量过期 key 如果永远不被访问，会一直占用内存。

**定期删除：**
- 每隔一段时间（默认每 100ms），随机抽取一部分设置了过期时间的 key，检查是否过期，过期就删除；
- 如果过期 key 占比超过 25%，就再次抽取，直到占比低于 25%，且单次扫描不超过 25ms，避免阻塞主线程。
- **优点**：平衡 CPU 和内存，既不会频繁扫描浪费 CPU，也不会让大量过期 key 占用内存；
- **缺点**：依然会有部分过期 key 没被扫描到，一直占用内存。

**两者结合：** 惰性删除处理访问到的过期 key，定期删除主动清理没被访问到的过期 key，既保证了性能，又尽可能释放了内存。

即使这样，还是会有过期键留在内存，这时候 **内存淘汰策略** 会起作用，在内存满的时候主动淘汰。

### 5. Redis 有哪些内存淘汰策略？生产怎么选？

**Q:** Redis 内存满了达到 `maxmemory` 上限怎么办？有哪些淘汰策略？生产怎么选？

**A:**

当 Redis 内存使用量达到配置的 `maxmemory` 上限时，Redis 会按照指定策略淘汰一部分 key，释放内存，保证新的写入能正常执行。

Redis 提供 8 种内存淘汰策略：

| 策略 | 含义 |
|------|------|
| **noeviction**（默认） | 内存满时，拒绝所有新的写入请求，返回错误，读请求正常 |
| **allkeys-lru** | 从所有 key 中，淘汰**最近最少使用**的 key |
| **allkeys-lfu** | 从所有 key 中，淘汰**访问频率最低**的 key（Redis 4.0+ 支持） |
| **allkeys-random** | 从所有 key 中，随机淘汰 |
| **volatile-lru** | 仅从**设置了过期时间**的 key 中，淘汰最近最少使用的 |
| **volatile-lfu** | 仅从**设置了过期时间**的 key 中，淘汰访问频率最低的 |
| **volatile-random** | 仅从**设置了过期时间**的 key 中，随机淘汰 |
| **volatile-ttl** | 仅从**设置了过期时间**的 key 中，优先淘汰剩余过期时间最短的 |

**生产环境选型建议：**
- **绝大多数缓存场景**：推荐 `allkeys-lru`，优先淘汰最近很少用的 key，保留热点数据，缓存命中率最高；
- **有明显冷热区分、突发流量场景（如秒杀）**：推荐 `allkeys-lfu`，优先淘汰访问频率低的 key，抗缓存污染能力更强；
- **需要区分持久化数据和缓存数据**：推荐 `volatile-lru`，只淘汰设置了过期时间的缓存 key，永久存储的 key 不会被淘汰；
- **绝对不允许数据丢失**：用 `noeviction`，但要做好内存监控，避免内存满了无法写入。

## 数据结构篇

### 6. 为什么 SDS 比 C 原生字符串好？

**Q:** Redis 为什么自己设计 SDS 不用 C 字符串？

**A:**

C 原生字符串：
- 长度需要用 `strlen` 遍历计算，O(n) 复杂度
- 不能存二进制（因为 `\0` 结尾）
- 修改长度容易缓冲区溢出

SDS 改进：
- **O(1) 获取长度**：结构体保存 len 属性，不用遍历
- **二进制安全**：不依赖 `\0` 结束，可以存任意二进制数据
- **空间预分配**：修改字符串时按需分配多余空间，减少内存分配次数
- **惰性空间释放**：缩短字符串时不立刻回收，留着给后面用

---

### 7. 跳表是什么？为什么 ZSet 用跳表不用红黑树？

**Q:** 有序集合为什么用跳表实现？

**A:**

**跳表核心思想**：在有序链表上增加多层索引，通过空间换时间，把查找复杂度从 O(n) 降到 O(log n)，相当于二分查找的链表实现。

**为什么不用红黑树：**
1. 跳表实现更简单，代码好写好调试
2. 跳表是有序的，范围查询非常方便（顺着往后遍历就行），红黑树范围查询要做中序遍历麻烦一些
3. 跳表插入删除更稳定，平均 O(log n)，不会像红黑树插入删除会频繁调整树结构
4. 跳表更容易做并发访问，调整只影响局部，不需要全树 rebalance

---

### 8. 什么是压缩列表？什么时候用压缩列表？

**Q:** 压缩列表是干什么的？为什么能省内存？

**A:**

压缩列表是 Redis 为了节省内存设计的一种特殊编码的连续内存数据结构。

**特点：**
- 所有元素连续存放在一块内存里，不存指针，省掉指针空间（64位系统一个指针8字节）
- 不同元素不同编码长度，小整数用更少字节存，极端一个整数只要 1 字节
- 缺点：插入删除可能需要连锁更新，因为每个元素的前置长度变了，所以只适合元素少、元素小的场景

**什么时候用：**
- Hash 当字段少、字段值小的时候用压缩列表
- ZSet 当元素少、元素小的时候用压缩列表
- 元素多了或者大了就转成哈希表/跳表

## 持久化篇

### 9. RDB 和 AOF 区别？各自优缺点？怎么选？

**Q:** Redis 两种持久化方式区别？

**A:**

**RDB（Redis Database）**：全量快照，把当前内存中所有数据生成一个二进制快照保存到磁盘。

**AOF（Append Only File）**：增量日志，把所有写命令追加到文件末尾，重启的时候重放一遍命令恢复数据。

| 对比维度 | RDB | AOF |
|----------|-----|-----|
| **文件大小** | 小（二进制压缩） | 大（明文命令，比 RDB 大） |
| **持久化方式** | 全量快照 | 增量追加 |
| **恢复速度** | 快（直接加载二进制） | 慢（要重放所有命令） |
| **数据安全性** | 容易丢数据，最后一次持久化之后的数据丢了 | 更安全，可以配置 fsync 策略，最多丢一秒数据 |
| **文件压缩** | 默认压缩 | 不压缩 |

**优缺点总结：**
- RDB 优点：文件小，恢复快，适合做备份；缺点：不能实时持久化，容易丢数据
- AOF 优点：数据安全，不容易丢；缺点：文件大，恢复慢

**生产怎么用：** 一般**同时开 RDB + AOF**，重启优先用 AOF 恢复数据，更完整；RDB 用来做备份。

---

### 10. RDB 触发机制是什么？

**Q:** 什么时候会触发 RDB 持久化？

**A:**

**两种触发：**

1. **自动触发**：满足 `save m n` 配置（比如 900 秒有至少 1 个键改变就自动 save）
2. **手动触发**：执行 `bgsave` 命令或者 `save` 命令
   - `bgsave`：后台异步执行 RDB，主线程继续处理请求，推荐
   - `save`：主线程直接执行，会阻塞所有请求，不推荐

**注意**：`bgsave` 是 fork 一个子进程来做 RDB，父进程继续处理请求。fork 过程会阻塞主线程，但是生成 RDB 过程不阻塞。

---

### 11. AOF 重写是什么？为什么要重写？

**Q:** AOF 为什么需要重写？怎么重写？

**A:**

**为什么要重写：** AOF 是追加命令，很多命令都是对同一个 key 重复修改，会导致 AOF 文件越来越大，里面很多无用命令（比如多次 increment 最后只需要保留最终值），重写就是把多余命令去掉，只保留最终结果，缩小 AOF 文件体积。

**怎么重写：**
- 后台开启一个子进程，遍历内存中所有数据，把每个 key 最终状态写成一条命令，写入新的 AOF 文件
- 新写入完成之后，原子替换旧文件，完成重写
- 重写过程中主线程继续处理请求，新的写命令同时写到旧 AOF 和重写缓冲区，保证不丢数据

---

### 12. Redis 持久化是主线程做的吗？会阻塞吗？

**Q:** RDB/AOF 会阻塞 Redis 主线程吗？

**A:**

- **RDB bgsave**：fork 子进程的时候会短暂阻塞主线程，生成 RDB 过程子进程做，不阻塞主线程
- **AOF 重写**：和 RDB bgsave 一样，fork 阶段阻塞，重写子进程做，不阻塞
- **AOF 刷盘**：如果是 `appendfsync everysec`，刷盘是后台线程做，不阻塞主线程

只有 fork 那一下会短暂阻塞，其他时候都不阻塞。

## 缓存问题篇

### 13. 什么是缓存穿透？问题原因是什么？怎么解决？

**Q:** 缓存穿透是什么意思？怎么预防？

**A:**

**问题定义：** 缓存穿透指的是大量请求查询缓存和数据库中都不存在的数据，导致每一次请求都绕过缓存直接打到数据库，最终把数据库压垮。

**产生原因：**
- 业务代码没做前置参数校验，放行了大量非法参数的请求；
- 恶意攻击、爬虫批量请求不存在的数据；
- 数据误删除，缓存和数据库都没了，但请求还在过来。

**解决方案（按优先级排序）：**

1. **接口层参数校验**：最前置、成本最低的方案。在入口层就拦截非法参数，比如 ID <= 0、格式非法的请求直接返回错误，不进入后续业务逻辑，从源头避免无效请求。

2. **缓存空值 / 默认值**：当数据库查询结果为空时，依然把空结果（空字符串、空数组）写入缓存，设置一个较短的过期时间（如 30~300 秒）。优点：实现简单，性价比极高；缺点：会占用少量内存，短时间内数据不一致。

3. **布隆过滤器拦截**：提前把所有合法的业务 ID（如全量商品 ID）写入布隆过滤器，请求过来先查布隆过滤器，如果过滤器判断 ID 不存在，直接返回错误，不访问缓存和数据库。优点：内存占用极小（1 亿条数据仅需 12MB 左右），拦截效率极高；缺点：存在极小的误判率，不支持删除数据。

适用场景：数据量极大、更新频率低的场景（如商品库、用户库）。

---

### 14. 什么是缓存击穿？问题原因是什么？怎么解决？

**Q:** 缓存击穿是什么？和缓存穿透、缓存雪崩区别是什么？怎么解决？

**A:**

**问题定义：** 缓存击穿指的是某个**热点 key**过期的瞬间，大量并发请求同时访问这个 key，缓存未命中，所有请求瞬间全部打到数据库，导致数据库压力骤增甚至宕机。

**和其他问题区别：**
- **缓存穿透**：缓存和数据库都不存在的数据，一直穿透；
- **缓存击穿**：单个热点 key 过期，大量请求并发进来；
- **缓存雪崩**：大量 key 同时过期 / 缓存整体不可用。

**产生原因：**
- 热点 key 设置了过期时间，到期瞬间大量并发请求；
- 缓存重建耗时较长（如复杂 SQL、多表联查），导致缓存空窗期被拉长。

**解决方案：**

1. **热点 key 永不过期**：对核心热点 key（如秒杀商品、首页热门榜单）不设置 Redis 物理过期时间，而是在 value 里设置逻辑过期时间，后台启动异步线程定时更新缓存，从根源上避免 key 过期导致的击穿。优点：零空窗期，性能最高；缺点：额外占用内存，需要维护异步更新逻辑。

2. **互斥锁（分布式锁）**：当缓存未命中时，不是直接查数据库，而是先获取分布式锁，只有获取到锁的请求才能查询数据库并更新缓存，其他请求等待重试，保证同一时间只有一个请求重建缓存。优点：数据强一致性，实现简单；缺点：并发量高时会有线程等待，性能略低。

---

### 15. 什么是缓存雪崩？问题原因是什么？怎么解决？

**Q:** 缓存雪崩是什么意思？和缓存击穿区别是什么？怎么预防？

**A:**

**问题定义：** 缓存雪崩指的是**大量缓存 key 在同一时间集体过期**，或者 **Redis 集群整体宕机**，导致所有请求全部打到数据库，数据库瞬间被海量请求压垮。

**和缓存击穿区别：** 击穿是单个热点 key 过期，雪崩是大量 key 同时失效 / Redis 整体不可用。

**产生原因：**
- 代码里给大量 key 设置了相同的过期时间（比如统一设置 1 小时过期），到期时集体失效；
- Redis 主节点宕机，从节点还没来得及接管，缓存服务整体不可用；
- 缓存集群网络分区、机房故障，导致缓存服务不可用。

**解决方案：**

1. **过期时间加随机值，避免同时失效**：给 key 的过期时间增加一个随机偏移量，比如原本统一设置 1 小时过期，改成 `3600 + random(0, 300)`，让 key 在 1 小时 ~ 1 小时 5 分钟内分散过期，避免集体失效。

2. **搭建 Redis 高可用集群**：采用「主从复制 + 哨兵模式」或「Redis Cluster 集群」，避免单节点故障导致整个缓存服务不可用；同时做好跨机房部署、容灾备份，提升集群可用性。

3. **服务限流降级 + 多级缓存**：
   - 限流：在服务入口设置限流，比如单机 QPS 限制 1000，超过的请求直接返回降级提示，避免把数据库打满；
   - 多级缓存：采用「本地缓存（进程内 LRU Cache）+ Redis 集群缓存」架构，Redis 宕机时，本地缓存依然能支撑一部分请求，避免所有流量直接打到数据库；
   - 熔断降级：当数据库请求失败率达到阈值时，触发熔断，直接返回降级数据（默认商品信息、提示语），保护数据库。

4. **热点数据永不过期**：对核心业务的热点数据，设置永不过期，后台异步更新，从根源避免过期导致的雪崩。

## 分布式锁篇

### 16. 分布式锁要满足哪些核心要求？常见问题有哪些？

**Q:** 为什么需要 Redis 分布式锁？分布式锁必须满足什么条件？

**A:**

**问题背景：** 分布式系统中，多个进程/服务器需要同时操作共享资源（比如库存扣减、订单创建），需要一个全局锁来保证同一时间只有一个进程能执行临界区代码，避免并发导致的数据错乱（比如超卖）。

**分布式锁必须满足的 4 个核心要求：**
1. **互斥性：** 同一时间只有一个客户端能持有锁；
2. **防死锁：** 即使持有锁的客户端崩溃，锁最终也能被释放，不会永久占用；
3. **解铃还须系铃人：** 只能释放自己加的锁，不能误删其他客户端的锁；
4. **原子性：** 加锁和释放锁的操作必须是原子的。

**常见问题与产生原因：**
1. **死锁问题：** 客户端加锁后崩溃，没有释放锁，锁永远不会过期 → 原因：没有设置过期时间，或加锁+设置过期不是原子操作；
2. **锁误删问题：** 客户端 A 的锁过期了，但业务还没执行完，客户端 B 此时加锁成功，客户端 A 执行完后误删了客户端 B 的锁 → 原因：释放锁时不校验持有者，直接删除；
3. **锁提前过期问题：** 业务执行时间超过了锁的过期时间，锁自动释放，导致并发问题 → 原因：过期时间设置不合理，没有续期机制；
4. **主从锁丢失问题：** 主节点加锁成功后还没同步给从节点就宕机，新主节点没有这个锁，其他客户端可以再次加锁 → 原因：主从异步复制导致锁丢失。

### 17. Redis 分布式锁基础实现怎么做？

**Q:** 最简单生产可用的 Redis 分布式锁怎么实现？

**A:**

核心思路：**原子加锁 + 唯一标识 + Lua 脚本原子解锁**。

**加锁：** 使用 `SET key random_value NX EX expire_time` 原子命令：
- `NX`：只有 key 不存在时才设置成功，保证互斥性；
- `EX`：设置过期时间，保证客户端崩溃后锁能自动释放，防死锁；
- `random_value`：唯一随机值，标识锁的持有者，用来防止误删。

**解锁：** 用 Lua 脚本保证「判断持有者 → 删除锁」整个过程是原子的：
```lua
if redis.call("GET", KEYS[1]) == ARGV[1] then
  return redis.call("DEL", KEYS[1])
else
  return 0
end
```
只有锁的 value 和自己一致，才允许删除，保证只能自己解自己的锁，不会误删。

这个基础方案解决了死锁和误删两个核心问题，大多数中小场景已经够用。

### 18. 锁提前过期怎么办？怎么实现锁续期？

**Q:** 业务执行时间超过锁过期时间，锁提前释放导致并发问题怎么解决？

**A:**

使用 **看门狗（Watch Dog）锁续期** 方案：

开启一个独立的守护线程，当锁快过期时，如果业务还没执行完，并且锁还是自己持有，就自动给锁续期，重置过期时间。

**核心流程：**
- 加锁成功后，启动看门狗线程；
- 每隔 `过期时间 / 3` 时间检查一次；
- 如果锁还存在且是自己持有，就调用 `EXPIRE` 命令重置过期时间；
- 释放锁后，停止看门狗线程。

这样业务不管执行多久，只要没执行完，锁就不会过期；只要客户端崩溃，看门狗也会停止，锁最终会过期释放，不会死锁。

### 19. 什么是 RedLock？解决什么问题？

**Q:** RedLock 红锁是什么？为什么需要它？

**A:**

RedLock 是 Redis 作者提出的一种**多实例分布式锁算法**，解决**单机 Redis 主从切换导致的锁丢失问题**。

**问题背景：** 单机 Redis 主从架构下，主节点加锁成功后，还没把锁同步给从节点就宕机了，从节点升主后没有这个锁，其他客户端可以再次加锁，导致同一时间两个客户端都持有锁，破坏互斥性。

**RedLock 算法流程：**
1. 获取当前时间戳；
2. 按顺序向 N 个（通常 5 个）**独立的 Redis 节点**请求加锁，每个实例都设置相同锁名和随机值，每个锁都有超时时间；
3. 只有超过半数（`N/2+1`）实例加锁成功，**并且总耗时小于锁超时时间**，才算加锁成功；
4. 释放锁：给所有实例都发释放锁命令。

**争议与现状：**
- RedLock 理论上更安全，但实际工程中依赖时钟同步，实现复杂，性能比单机锁差；
- 现在工业界大多数观点认为：普通业务场景单机锁已经够用，对一致性要求极高的场景用 Zookeeper 做分布式锁比 RedLock 更简单可靠。

### 21. 什么是 BigKey 大 Key 问题？产生什么危害？怎么解决？

**Q:** 生产环境 BigKey 会导致什么问题？怎么排查和解决？

**A:**

**BigKey 定义：** 指的是 key 对应的 value 占用内存过大，或者集合类型元素数量过多的 key。行业通用判定标准：
- 字符串类型：value 超过 10KB 就算大 Key，超过 1MB 就算超大 Key；
- 集合类型（Hash/List/Set/ZSet）：元素数量超过 1 万个，就算大 Key。

**产生的危害：**
1. **Redis 阻塞：** 读写 BigKey 会占用大量 CPU 和 IO 资源，导致 Redis 阻塞，其他命令排队等待，接口超时；
2. **内存溢出 OOM：** BigKey 占用大量内存，甚至导致 Redis 内存溢出；
3. **网络阻塞：** 传输 BigKey 占用大量带宽，影响其他服务；
4. **主从同步异常：** BigKey 同步会导致主从延迟增大，甚至主从断开。

**产生原因：**
- 业务设计不合理，把大量数据存在一个 key 里；
- 没有定期清理，比如消息队列 List 只生产不消费，元素越来越多；
- 集合类型不断追加，没有做分片拆分。

**解决方案：**
1. **BigKey 拆分**（核心方案）：把大 Key 拆分成多个小 Key，比如把全量用户列表按时间拆分成 `mylist:202405`、`mylist:202406` 等多个小 List；
2. **分批读取/删除**：对已存在的 BigKey，不要一次性读写删除，分批操作，每次间隔一点时间，避免阻塞 Redis；
3. **优化数据结构**：用 Bitmap、HyperLogLog 替代 Set 做海量数据统计，大幅降低内存；用 Stream 替代 List 做消息队列，避免堆积；
4. **使用异步删除**：不要用 `DEL` 删除大 key，用 `UNLINK` 异步删除，后台慢慢释放不阻塞主线程；
5. **定期巡检**：用 `redis-cli --bigkeys` 命令定期扫描，提前发现并优化。

### 22. 什么是 HotKey 热 Key 问题？产生什么危害？怎么解决？

**Q:** 生产环境热 Key 会导致什么问题？怎么解决？

**A:**

**HotKey 定义：** 指某个 key 在短时间内被大量并发请求访问，比如秒杀商品、热门榜单、热搜词条，每秒被请求几万次。

**产生的危害：**
1. **Redis 节点 CPU 打满**：大量请求集中在一个节点，CPU 被打满，导致节点响应变慢甚至宕机；
2. **缓存击穿**：热 Key 过期瞬间，大量请求同时打到数据库，导致数据库宕机；
3. **网络带宽打满**：大量请求占用服务器带宽，影响其他服务。

**产生原因：** 突发热点事件（秒杀、热搜）、业务设计不合理流量集中。

**解决方案：**
1. **本地缓存（二级缓存）**（最常用方案）：在应用服务本地缓存热 Key（如使用 `lru_cache`），请求先查本地缓存，命中直接返回，把流量分散到各个应用服务器，彻底解决 Redis 节点压力。注意设置较短过期时间（1-5 秒）避免数据不一致。
2. **热 Key 分片备份**：把热 Key 复制多个副本（`hotkey:1` ~ `hotkey:10`），分散到不同 Redis 节点，请求时随机访问一个备份，流量分散到多个节点，避免单个节点压力过大。
3. **热 Key 永不过期**：对核心热 Key 不设置物理过期时间，后台异步更新缓存，从根源避免过期导致的缓存击穿。
4. **流量限流、熔断**：对热 Key 请求做限流，超过阈值直接返回降级数据，避免流量过大打垮 Redis 和数据库。

### 23. Redis 为什么会产生缓冲区溢出？怎么解决？

**Q:** 复制缓冲区溢出是什么问题？

**A:**

全量复制的时候，主节点生成 RDB 之后，把这期间新的写命令存在复制缓冲区，发给从节点。如果从节点网络慢，或者 RDB 生成太慢，缓冲区满了就会溢出，导致复制失败断开重连，恶性循环。

解决：调大 `client-output-buffer-limit slave` 配置。

---

### 24. Redis 管道 pipeline 有什么用？原理是什么？

**Q:** pipeline 为什么能提速？

**A:**

pipeline 就是把多个命令打包一次性发给 Redis，减少网络往返次数。

- 不使用 pipeline：N 个命令需要 N 次网络往返，每次往返耗时主要是网络延迟
- 使用 pipeline：一次性把 N 个命令发过去，结果一次性回来，只需要 1 次网络往返

**注意：** pipeline 打包的命令不能太多，不然一次发包太大也会慢。

### 25. 如何用 Redis List 实现消息队列？

**Q:** 怎么用 Redis List 做简单消息队列？怎么解决消息丢失？

**A:**

**基础方案：LPUSH + BRPOP**
- **生产者**：`LPUSH queue message` → 从队列头部插入消息
- **消费者**：`BRPOP queue 0` → 从队列尾部阻塞拉取消息，队列空时阻塞等待不占 CPU
- 优点：实现简单，实时性高，不会空轮询
- 缺点：消费者拉取后崩溃，消息就丢了（已经从队列移除了）

**改进方案（可靠消费）：BRPOPLPUSH + 双队列**
1. 两个队列：`queue:pending`（待消费） + `queue:processing`（处理中）
2. 消费者拉取：用 `BRPOPLPUSH` 从 `pending` 移到 `processing`
3. 处理成功：从 `processing` 删除
4. 消费者崩溃后，**定时巡检**把 `processing` 中超时的消息移回 `pending` 重试
5. 这样就保证了消息至少消费一次，不会丢失

**适用场景：** 轻量级消息队列，对可靠性要求不是极高，追求简单快；复杂场景建议用专业 MQ（Kafka/RabbitMQ）。

### 26. Redis Pub/Sub 和 Stream 区别？怎么选？

**Q:** Redis 的发布订阅 Pub/Sub 和 Stream 有什么区别？各自适用什么场景？

**A:**

| 对比维度 | Pub/Sub | Stream |
|----------|---------|--------|
| **核心定位** | 实时广播通信 | 专业持久化消息队列 |
| **消息持久化** | ❌ 不支持，发完即丢 | ✅ 原生支持，重启不丢 |
| **离线消息** | ❌ 不支持，离线消息全丢 | ✅ 支持，上线后继续消费 |
| **消息回溯** | ❌ 不支持 | ✅ 支持，按 ID 任意回溯 |
| **消息确认 ACK** | ❌ 无 | ✅ 原生支持，未 ACK 可重试 |
| **消费模式** | 仅广播 | 支持双模式：广播 / 同消费组负载均衡 |
| **多消费者负载均衡** | ❌ 不支持 | ✅ 原生支持，同组自动分摊 |
| **消息堆积能力** | ❌ 极差，缓冲区满了断连 | ✅ 极强，支持百万级堆积 |
| **实时性** | 极致（微秒-毫秒） | 优秀（毫秒，满足需求） |
| **消息丢失风险** | 极高 | 极低 |

**选择：**
- **Pub/Sub** → 适合**实时广播场景**：在线通知、配置刷新、弹幕推送
- **Stream** → 适合**业务消息队列**：异步处理、订单流程、削峰填谷、可靠消息投递

## 集群高可用篇

### 27. 主从复制原理是什么？

**Q:** Redis 主从复制怎么工作的？

**A:**

**全量复制 + 增量复制：**

1. **同步阶段**：从节点连接主节点，触发全量复制，主节点生成 RDB 快照发给从节点，从节点加载 RDB
2. **命令传播阶段**：全量同步完成之后，主节点把这期间新的写命令发给从节点，从节点执行，保持一致
3. **后续增量复制**：主节点每接收一个写命令，就同步给所有从节点

**断点续传**：现在 Redis 支持增量复制，如果从节点断开重连，只需要同步断开期间缺少的命令，不用全量重传。

### 28. 哨兵机制是什么？哨兵怎么选主？

**Q:** 哨兵解决什么问题？Leader 选举怎么选？

**A:**

**哨兵作用：**
1. **监控**：不断检查主节点和从节点是否存活
2. **自动故障转移**：主节点宕机了，自动从从节点选一个升主，把其他从节点指向新主，通知客户端地址变更
3. **配置中心**：客户端可以问哨兵当前主节点是谁

**选主流程：**
1. 首先过滤掉宕机的从节点
2. 然后选择**优先级最高**的从节点（优先级配置越小越高）
3. 优先级一样选**复制偏移量最大**的（复制的数据最完整最新）
4. 都一样选**runid 最小**的节点

### 29. 什么是 Redis 脑裂？怎么解决？

**Q:** Redis 脑裂是什么问题？产生原因是什么？怎么解决数据丢失？

**A:**

**问题定义：** Redis 脑裂指的是因为**网络分区**导致集群中同时出现两个主节点：
- 原主节点和从节点、哨兵集群断开连接，但原主节点本身还能正常运行；
- 哨兵判定原主节点下线，选举出一个新的主节点；
- 此时集群同时存在两个主节点，客户端还在向旧主写入数据；
- 网络恢复后，旧主降级为从节点，同步新主数据，网络分区期间写入旧主的数据会全部丢失。

**产生原因：**
1. 主节点所在服务器网络故障，和从节点、哨兵断开，但和客户端网络正常；
2. 主节点服务器 CPU 满载、内存不足、GC 卡顿，无法响应哨兵心跳，被误判下线；
3. 机房网络分区，主节点所在网段和从节点、哨兵网段不通。

**解决方案：** 通过两个核心配置从根源避免数据丢失，**生产环境必须配置：**

```
min-replicas-to-write 1
min-replicas-max-lag 10
```

- `min-replicas-to-write 1`：主节点至少要有 1 个健康的从节点保持连接，才允许写入数据；
- `min-replicas-max-lag 10`：从节点的复制延迟最大不能超过 10 秒，否则主节点拒绝写入。

**工作原理：** 当发生网络分区，主节点和从节点断开连接后，不满足 `min-replicas-to-write` 条件，主节点直接拒绝所有新的写入请求，客户端报错，不会再向旧主写入数据。网络恢复后，旧主降级同步，不会丢失数据。

**额外优化：**
- 优化机房网络架构，避免网络分区；
- 监控主节点 CPU、内存、网络状态，提前预警故障；
- 合理设置哨兵 `down-after-milliseconds`，避免过早误判下线。

### 30. Redis 集群分片原理是什么？

**Q:** Redis 集群怎么分片的？怎么找到 key 在哪个节点？

**A:**

Redis 集群采用 **hash slot（哈希槽）** 分片：

- 整个集群固定分成 **16384 个槽**
- 对 key 用 `CRC16(key) % 16384` 得到槽号，然后映射到对应节点
- 每个节点负责一部分槽，增减节点只需要移动槽就行，不用全部重新分配
- 支持批量操作，只要 key 在同一个 slot 可以 mget 等

**ASK 转向 vs MOVED 转向：**
- MOVED：槽已经稳定归到另一个节点了，告诉客户端永久重定向
- ASK：正在进行槽迁移，当前槽不在这里，让客户端去目标节点问一下，是临时重定向

### 31. 什么是 RedLock？为什么需要 RedLock？

**Q:** 分布式锁用 Redis 怎么实现？RedLock 是什么？

**A:**

> 本题核心内容已放在「分布式锁篇」详细展开，这里补充集群环境下的总结：

**单机 Redis 实现分布式锁：**
- `SET lock_key random_value NX PX 30000` （NX 不存在才设置，PX 设置过期时间防止死锁）
- 释放锁用 Lua 脚本：`if redis.call('get',KEYS[1]) == ARGV[1] then return redis.call('del',KEYS[1]) else return 0 end`，判断是自己的锁才删除

**为什么需要 RedLock：** 单机 Redis 做分布式锁，主从切换可能导致锁丢失，RedLock 是多实例 Redis 实现分布式锁，提升安全性。

**RedLock 算法流程：**
1. 获取当前时间戳
2. 按顺序向 N 个（一般 5 个）独立 Redis 实例请求加锁，每个实例都设置相同锁名和随机值，每个锁都有超时时间，只有超过半数（N/2+1）实例加锁成功，并且总耗时小于锁超时，才算加锁成功
3. 释放锁：给所有实例都发释放锁命令

**争议：** RedLock 理论上很完美，但实际工程中依赖时钟同步，实现复杂性能差，现在多数观点认为大多数场景单机+看门狗已经够用，对一致性要求极高的场景用 Zookeeper 更简单可靠。

## 总结速记

| 考点 | 核心结论 |
|------|---------|
| Redis 为什么快 | 纯内存、IO 多路复用、单线程无锁竞争 |
| 过期删除 | 惰性删除 + 定期删除，过期没删靠内存淘汰 |
| 内存淘汰 | 生产一般用 allkeys-lru / allkeys-lfu |
| RDB vs AOF | RDB 全量快照文件小恢复快，AOF 增量更安全，一般都开 |
| 缓存穿透 | 查不到的数据一直打DB → 接口校验 / 缓存空值 / 布隆过滤器 |
| 缓存击穿 | 热点 key 过期大量请求打DB → 互斥锁 / 永不过期 |
| 缓存雪崩 | 大量 key 同时过期 / 缓存宕机 → 均匀过期、高可用、限流降级 |
| Redis 为什么快 | 全内存 + 单线程命令 + IO 多路复用 + 极致数据结构 |
| Redis 6.0 多线程 | 只做网络IO和协议解析，核心命令仍单线程 |
| 分布式锁核心要求 | 互斥、防死锁、谁加谁解、原子性 |
| 分布式锁基础实现 | SET NX EX 原子加锁 + 唯一标识 + Lua 原子解锁 |
| 锁提前过期解决 | 看门狗自动续期，业务没完自动重置过期时间 |
| Redis 脑裂 | 网络分区出两个主，数据丢失 → min-replicas-to-write 配置解决 |
| RedLock | 多实例过半加锁，解决主从锁丢失，工程争议大 |
| 跳表为什么好 | 实现简单、范围查询方便、插入删除稳定 |
| 主从复制 | 全量同步 + 增量命令传播 |
| 哨兵作用 | 监控、自动故障转移、选主 |
| 集群分片 | 16384 个哈希槽，CRC16 取模定位节点 |

## 场景实践篇：自己实现 vs Redis 实现对比

Redis 的核心价值：用极低开发成本，解决了「自己实现」极其复杂甚至不可能解决的问题。只要涉及「分布式、大数据量、高可靠、高性能」，用 Redis 能节省 90% 以上开发成本，稳定性和性能是自己实现的几十倍。

### 1. 缓存 (Cache)

| 维度 | 自己实现（Python dict） | Redis 实现 |
|------|----------|------------|
| 开发复杂度 | ⭐ (简单) | ⭐ (简单) |
| 单机性能 | ⭐⭐⭐⭐⭐ (极快) | ⭐⭐⭐⭐ (足够快) |
| 分布式支持 | ❌ 不支持 | ✅ 天然支持 |
| 数据可靠性 | ❌ 重启丢 | ✅ 持久化保障 |
| 生产可用 | ❌ 仅适合测试 | ✅ 互联网标配 |

**自己实现的问题：**
- 内存限制：数据大了直接 OOM
- 并发问题：多线程需要加锁，多进程无法共享
- 重启丢失：程序重启缓存全没
- 无法分布式：多台服务器缓存重复，命中率极低

**Redis 优势：**
- 专业内存管理：支持 LRU/LFU 淘汰，自动清理冷数据
- 天然高并发：单线程模型，无需加锁，并发性能极高
- 持久化保障：RDB/AOF 持久化，重启不丢
- 分布式共享：多服务器共享一份缓存，命中率高

**自己实现的问题：**
- 仅单机有效：多进程/多服务器完全失效，会超卖

- 身份验证：唯一 value 标识持有者，只有自己能释放
- 高可用：主从+哨兵保障可用性
