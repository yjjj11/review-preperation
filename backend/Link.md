## 计算机网络高频问答整理

### 1. 客户端怎么验证证书合法性？

**Q:** HTTPS 握手时，客户端如何验证服务端证书是否合法？

**A:**

证书生成过程：
- 首先 CA 会把持有者的公钥、用途、颁发者、有效时间等信息打成一个包，然后对这些信息进行 Hash 计算，得到一个 Hash 值；
- 然后 CA 会使用自己的私钥将该 Hash 值加密，生成 Certificate Signature，也就是 CA 对证书做了签名；
- 最后将 Certificate Signature 添加在文件证书上，形成数字证书；
- 在进行第一次握手的时候，服务端直接把证书传递给客户端。

客户端验证过程：
- 首先客户端会使用同样的 Hash 算法获取该证书的 Hash 值 H1；
- 通常浏览器和操作系统中集成了 CA 的公钥信息，浏览器收到证书后可以使用 CA 的公钥解密 Certificate Signature 内容，得到一个 Hash 值 H2；
- 最后比较 H1 和 H2，如果值相同，则为可信赖的证书，否则则认为证书不可信。
- 假如在 HTTPS 的通信过程中，中间人篡改了证书原文，由于他没有 CA 机构的私钥，所以 CA 公钥解密的内容就不一致。

### 2. 分布式环境下 Session 怎么处理？

**Q:** 分布式环境下，客户端请求经过负载均衡，可能会分配到不同的服务器上，假如一个用户的请求两次没有落到同一台服务器上，那么在新的服务器上就没有记录用户状态的 Session。这时候怎么办呢？

**A:**

可以使用 Redis 等分布式缓存来存储 Session，在多台服务器之间共享 Session 数据，所有服务器都从 Redis 读取 Session，就能解决分布式 Session 问题。

### 3. 如果第三次握手丢了，会怎么样？

**Q:** TCP 三次握手第三次握手 ACK 丢了，双方会怎么处理？

**A:**

- **客户端**：认为连接已经成功，直接发送数据；实际上服务端没有收到 ACK，还没认为连接建立成功。
- **服务端**：会重传 SYN+ACK 多次失败后，放弃连接，accept() 报错；
- 最终服务端收到客户端数据后，发 RST 复位包关闭连接，客户端才知道连接失败，直接进入 CLOSED 阶段。

### 4. 第二次握手传回了 ACK，为什么还要传回 SYN？

**Q:** 第二次握手为什么需要同时带 SYN？

**A:**

- **ACK 作用**：确认客户端的 SYN，验证报文来源，完成「确认」功能；
- **SYN 作用**：同步服务端自己的初始序号，任何一方发送数据前都必须同步自己的初始序号。SYN + seq 就是为了把自己的初始序号发给对方同步。

TCP 连接是双向的，双方都需要同步各自的初始序号，所以第二次握手必须同时带 ACK 和 SYN。

### 5. 怎么应对 SYN flood（DDoS）攻击？

**Q:** SYN flood 攻击是什么？怎么防范？

**A:**

**SYN flood**：攻击者大量发送 SYN 包，不回复第三次 ACK，占满服务端半连接队列，让正常用户无法连接。

常见防范方法：

- **syn cookie**：在收到 SYN 包后，服务器根据一定的方法，以数据包的源地址、端口等信息为参数计算出一个 cookie 值作为自己的 SYNACK 包的序列号，回复 SYN+ACK 后，服务器并不立即分配资源进行处理，等收到发送方的 ACK 包后，重新根据数据包的源地址、端口计算该包中的确认序列号是否正确，如果正确则建立连接，否则丢弃该包。实际上可以理解为不提前占半连接队列资源。
- **SYN Proxy 防火墙**：服务器防火墙会对收到的每一个 SYN 报文进行代理和回应，并保持半连接。等发送方将 ACK 包返回后，再重新构造 SYN 包发到服务器，建立真正的 TCP 连接。

### 6. 保活计时器有什么用？

**Q:** TCP 为什么需要保活计时器？

**A:**

解决客户端突然宕机、服务端无限等待的问题：

- 服务端每收到客户端数据，重置保活计时器（默认 2 小时）；
- 超时后，每隔 75 秒发探测报文，连续 10 次无响应则关闭连接；
- 释放资源，避免浪费。

### 7. 为什么挥手的时候客户端收到第二次挥手不能直接关闭？

**Q:** TIME_WAIT 为什么要等 2MSL？直接关闭不行吗？

**A:**

防止旧连接的残留数据包干扰新连接：如果客户端收到服务端的 FIN 报文之后立即关闭连接，但是此时服务端对应的端口并没有关闭，如果客户端在相同端口建立新的连接，可能会导致新连接收到旧连接残留的数据包，导致不可预料的异常发生。

所以 TIME_WAIT 等 2MSL（最长报文寿命），让网络上所有残留的报文都消失，再关闭连接就安全了。

### 8. 说说 TCP 报文首部的格式？

**Q:** TCP 首部包含哪些字段？各有什么用？

**A:**

- **源 / 目的端口号**（16 位 × 2）：定位通信进程，找到对应进程。
- **序号 / 确认号**（32 位 × 2）：序号标识当前报文第一个数据字节在流中的位置；确认号表示期望收到下一字节的序号，确认前序所有数据都收到了。
- **首部长度**（4 位）：单位是 4 字节，最大 60 字节（因为选项最多 40 字节）。
- **标志位**（6 位）：URG/ACK/PSH/RST/SYN/FIN，控制连接状态与数据传输。
- **窗口大小**（16 位）：告诉对方我这边接收缓冲区还有多大，用于流量控制。
- **校验和**（16 位）：校验首部 + 数据，保证传输可靠性。
- **紧急指针**（16 位）：紧急数据偏移，仅 URG=1 时有效，标识紧急数据在哪里。

### 9. 什么是快速恢复？

**Q:** TCP 拥塞控制中的快速恢复是什么作用？

**A:**

快速恢复与快速重传配套使用，收到 3 个重复 ACK 时触发（说明网络丢了一个包，但网络其实还能通，不需要等待 RTO 超时重传）。

进入前先更新参数：`cwnd = cwnd / 2`，`ssthresh = cwnd`。

核心流程：
- `cwnd = ssthresh + 3`（3 个重复 ACK 对应 3 个空闲额度，允许重传丢包 + 利用剩余带宽）
- 每收到 1 个重复 ACK，`cwnd += 1`（后续包成功到达，动态抬升窗口，避免速率过低）
- 收到新数据 ACK 后，`cwnd = ssthresh`，恢复正常拥塞避免（线性增长）

核心作用：温和降速 + 精准利用带宽，避免超时重传的断崖式性能损失，平衡可靠性与吞吐量。

### 10. TCP 服务端最大连接数受什么限制？

**Q:** TCP 服务端最多能支持多少个连接？有哪三大限制？

**A:**

TCP 服务端最大连接数主要受三大限制：

**1. 文件描述符限制（最关键）**
- 一个 TCP 连接占用一个文件描述符（fd）
- Linux 默认单进程限制 1024，调整 `ulimit -n 100000` 即可支持大量连接

**2. 内存限制**
- 每个空闲连接大约占用 3~5KB 内存
- 最大连接数 ≈ 系统总内存 / 单连接内存开销
- 连接不收发数据时，只占内存、不占 CPU，所以内存是核心限制之一

**3. 四元组限制（理论上限，服务端不碰）**
- 连接由「源 IP + 源端口 + 目标 IP + 目标端口」唯一标识
- **服务端只监听一个端口，不会被端口数量限制**，理论连接数几乎无上限；真正限制只有文件描述符 + 内存
- 客户端才受本地端口数量限制（端口总共 65535 个），服务端不受这个限制

**面试一句话总结：** TCP 服务端最大连接数不受端口限制，主要受文件描述符和内存限制；理论上限极大，实际可达几十万连接。

### 11. CLOSE_WAIT 和 TIME_WAIT 有什么区别？过多会有什么问题？怎么解决？

**Q:** TCP 四次挥手过程中，CLOSE_WAIT 和 TIME_WAIT 分别是什么状态？过多会导致什么问题？

**A:**

| 对比维度 | CLOSE_WAIT | TIME_WAIT |
|----------|------------|-----------|
| **谁进入这个状态** | 被动关闭连接的一方（对方主动关） | 主动关闭连接的一方（我方主动关） |
| **产生时机** | 对方发 FIN 过来，我方内核回复 ACK 后，等待应用层调用 close | 四次挥手最后一步，我方发完最后一个 ACK 后 |
| **要等待什么** | 等待应用层执行 close 关闭连接 | 等待 2MSL（最长报文寿命）后再真正关闭 |
| **过多原因** | 代码bug，连接使用完后**应用层忘记调用 close**，一直不释放 | 短连接高并发场景，频繁建立关闭连接，大量连接需要等 2MSL |
| **造成问题** | 一直占着文件描述符，连接泄漏，最终fd耗尽，无法建立新连接 | 占满本地临时端口，无法建立新的 outbound 连接；占用fd |
| **解决方法** | 修复代码bug，确保连接使用完后一定调用close；使用连接池及时回收 | 1. 开启 `tcp_tw_reuse` 允许复用端口；2. 调整 MSL 缩短等待时间；3. 改用长连接减少频繁关闭 |

**核心原因一句话：**
- **CLOSE_WAIT 过多** → **代码连接泄漏**，应用层没调 close
- **TIME_WAIT 过多** → **短连接高并发**，大量主动关闭都需要等 2MSL

### 12. 服务端如何判定 TCP 连接已经断开？有哪几种方法？

**Q:** 怎么知道对端连接已经断开了？常见判定方法有哪些？

**A:**

服务端判定连接断开，通常有五种方法：

1. **读返回 0**：`read()` 返回 0，说明对端正常挥手关闭，对方发了 FIN，读到 EOF
2. **读返回 -1 且非 EAGAIN**：读取错误且不是"暂时没数据"（EAGAIN/EWOULDBLOCK），说明连接异常重置（对端 RST 复位）
3. **epoll 捕获挂断事件**：epoll 能收到 `EPOLLHUP`（挂起）、`EPOLLRDHUP`（对端关闭读半连接）事件，直接判定断开
4. **应用层心跳超时**：应用层自己实现心跳包，定期发心跳，多久没收到心跳响应，判定连接僵死断开
5. **TCP Keepalive 内核探测**：开启 TCP 自带的 keepalive 选项，内核定期探测对端，如果几次探测都没响应，内核自动断开连接

**生产推荐：** 一般会**应用层心跳 + TCP Keepalive 配合使用**，应用层心跳处理逻辑层僵死，TCP Keepalive 处理网络层面死连接释放。

### 13. 解释 WebSocket 协议及其在网络编程中的应用？为什么需要 WebSocket？

**Q:** HTTP 不行吗？为什么需要 WebSocket？握手过程是什么样的？

**A:**

**传统 HTTP 的痛点：**
HTTP 是**短连接、单向请求-响应模型**：只能客户端主动发请求，服务端无法主动推送数据；要实现实时通讯只能用轮询、长轮询，开销大、延迟高，无法满足低延迟实时需求。

**WebSocket 核心定义：**
WebSocket 是**基于 TCP 的全双工长连接应用层协议**，解决了 HTTP 无法主动推送的问题：
- 一次握手，永久长连接，不用每次请求都三次握手
- 全双工通信：客户端和服务端可以随时互相发送数据
- 二进制帧传输，开销小，延迟低

**握手流程：**
1. **客户端发起握手**：基于 HTTP 发起升级请求，携带特殊头：
   ```http
   Upgrade: websocket
   Connection: Upgrade
   Sec-WebSocket-Key: 随机密钥
   ```
2. **服务端响应握手**：返回 `101 Switching Protocols`，响应 `Sec-WebSocket-Accept`（根据客户端密钥算法生成）
3. **握手成功**：之后断开 HTTP 语义，切换为 WebSocket 二进制帧通信，双方可以随时全双工发送数据

**常见应用场景：**
- 即时通讯（聊天、客服）
- 直播间弹幕、实时评论
- 实时数据推送（股票行情、监控数据）
- IoT 设备实时通信
- 在线协同文档/表格

## MySQL 高频问答整理

### 1. MyISAM 与 InnoDB 的区别是什么？

**Q:** MySQL 两个常用存储引擎核心区别？怎么选？

**A:**

最核心区别在于对事务的支持：

- **InnoDB**：支持事务，实现了 ACID 特性，非常适合需要高可靠性的场景，比如在线交易。为了支持事务，InnoDB 提供了**行级锁**和 **MVCC**，在高并发读写下性能表现很好。
- **MyISAM**：不支持事务，使用的是**表级锁**，写操作会锁住整张表，所以在写入并发量大的时候性能会比较差，但它的结构相对简单，读取速度很快，比较适合一些**读多写少**的应用场景。

---

### 2. in 和 exists 区别？

**Q:** SQL 查询中 in 和 exists 怎么选？性能区别是什么？

**A:**

in 和 exists 主要用在子查询中，它们的执行逻辑不同，性能差异取决于数据量分布：

**通用法则：小表驱动大表。**

- 如果**子查询结果集小**，**主查询表大**，那么用 `in` 效率会比较高。因为 in 会先执行子查询，然后把结果缓存起来，再去主查询的表里匹配。
- 如果**子查询表大**，**主查询表小**，那么用 `exists` 会更好。因为 exists 是拿主查询表里的每一行记录，去子查询的表里做一个判断，看是否存在匹配。

另外，对于 `not in` 和 `not exists`，一般推荐使用 `not exists`，因为 `not in` 在很多情况下无法有效利用索引，会导致全表扫描。

---

### 3. 删除表的时候 drop、delete 与 truncate 的区别是什么？

**Q:** 三个删除命令区别在哪里？

**A:**

三个命令删除级别完全不同：

- **delete**：是 DML 语言，它是一行一行地删除记录，可以带 WHERE 子句只删除部分数据。因为是事务性操作，所以 delete 的删除是**可以回滚**的，并且会触发触发器。
- **truncate**：是 DDL 语言，它会直接删除表里的所有数据，保留表结构，不能带 WHERE 子句。它相当于重建了表，所以速度非常快，**不能回滚**，也不会触发触发器。
- **drop**：也是 DDL 语言，它是最彻底的，会直接把整张表，包括表结构、数据、索引、约束等全部从数据库里删除掉，当然也不能回滚。

### 4. MySQL 索引失效常见场景

**Q:** 哪些情况索引会失效？

**A:**

- **范围查询**（> < >= <= between）：并非必然失效，数据量小走索引、数据量超过 20%~30% 时因回表代价过高，优化器会选择全表扫描导致索引失效。
- **字段类型不一致**：隐式类型转换导致索引失效
- **索引列上用函数**：比如 `DATE(create_time)`，会导致索引失效
- **索引列做运算**：`+ - * /` 等运算操作，索引失效
- **OR 连接不同字段**：索引失效（同字段 OR 有效）
- **左模糊查询**：`LIKE '%xx'`，索引失效（`LIKE 'xx%'` 有效）

### 5. 为什么官方建议使用自增长主键作为索引？

**Q:** InnoDB 为什么推荐自增主键？UUID 为什么不好？

**A:**

自增主键插入为顺序追加，仅在页满时新增页，页分裂影响极小；随机主键（如 UUID）插入需要插入页中间，频繁触发页分裂与数据挪动，性能损耗大且容易导致索引碎片化。

---

### 6. 如何查看 MySQL 死锁日志？怎么解决线上死锁问题？

**Q:** 线上出现死锁了怎么排查解决？

**A:**

**查看死锁日志：**
执行命令：`SHOW ENGINE INNODB STATUS;`
定位日志中 `LATEST DETECTED DEADLOCK` 段，重点关注：
- 涉及的两个事务（TRANSACTION 1/2）
- 事务持有的锁（HOLDS THE LOCK (S)）
- 事务等待的锁（WAITING FOR THIS LOCK）
- MySQL 回滚的哪个事务

**解决死锁问题：**
- **短期应急**：`KILL` 持有锁的 MySQL 线程 ID，快速恢复业务。
- **长期根治**：
  1. 统一加锁顺序：多表操作时，所有事务按相同顺序加锁
  2. 拆分大事务：缩短锁持有时间，降低冲突概率
  3. 优化索引：避免无索引导致的全表扫描和不必要的锁

### 7. 什么是 MySQL 两阶段提交？为什么需要两阶段提交？

**Q:** redo log 和 binlog 为什么需要两阶段提交？流程是什么？

**A:**

两阶段提交是 MySQL 内部为了保证数据一致性而设计的一种分布式事务协调机制，它主要用来协调 InnoDB 的 redo log 和 Server 层的 binlog 这两个独立日志的写入。它把事务的提交分成了两个阶段：

**准备阶段（Prepare）**：当 InnoDB 写完 redo log 后，它不直接提交事务，而是将 redo log 的状态设置为 "prepare"，此时 redo log 存在 redo log 环形缓冲区中，要把它刷到磁盘redolog file中。

**提交阶段（Commit）**：之后，由执行器去写 binlog。当 binlog 成功写入磁盘后，执行器再通知 InnoDB，将 redo log 的状态从 "prepare" 改为 "commit" ，完成整个事务的提交。

**为什么需要**：保证 redo log 和 binlog 两份日志的一致性。如果不做两阶段提交，先写哪个都会 crash 后不一致。

### 8. binlog 刷盘成功但 redo commit 前宕机，MySQL 如何保证一致性？

**Q:** binlog 刷盘成功但 redo commit 前宕机，MySQL 如何保证主从一致？

**A:**

MySQL 重启时触发崩溃恢复，步骤为：
1. 扫描 redo log 找出所有 prepare 状态事务；
2. 按事务 XID 校验磁盘 binlog，若存在对应完整事务，则强制将 redo log 标记为 commit 完成提交；
3. 最终主库数据与已同步 binlog 的从库保持一致。

### 9. 如何使用 EXPLAIN 分析 SQL 执行计划？核心看哪些字段？

**Q:** EXPLAIN 结果怎么看？重点看哪几个字段？

**A:**

在 SELECT 前加 EXPLAIN 即可查看 MySQL 优化器的执行计划。核心关注以下字段：
- **id**：执行顺序，id 越大越先执行。
- **type**：访问类型，性能关键指标。
- **key**：实际使用的索引。
- **rows**：估算扫描行数，越小越好。
- **Extra**：附加信息，判断优化情况。

### 10. type 字段的性能排序？哪些是必须优化的？

**Q:** type 字段不同值性能好坏怎么排序？哪些值必须优化？

**A:**

性能从优到劣排序：`system > const > eq_ref > ref > range > index > ALL`

目标：尽量达到 range 或以上。
红线：避免 ALL（全表扫描）。

### 11. Extra 中常见的关键值分别代表什么？

**Q:** EXPLAIN 的 Extra 字段各个值什么意思？

**A:**

- **Using index**：使用了覆盖索引，性能优秀。
- **Using where**：存储引擎返回数据后，Server 层再过滤。
- **Using temporary**：使用临时表，常见于 GROUP BY，性能差。
- **Using filesort**：外部排序，说明 ORDER BY 字段无索引，性能差。
- **Using index condition**：使用了索引下推，优化良好。

### 12. 如何通过 EXPLAIN 判断索引是否生效？

**Q:** 怎么看 EXPLAIN 结果知道索引用上了没有？

**A:**

- 看 **key** 字段：不为 NULL 表示用到了索引。
- 看 **type** 字段：不是 index 或 ALL，表示索引有效。
- 看 **key_len** 字段：长度越长，说明联合索引使用得越充分。

### 13. MySQL 深分页（如 LIMIT 1000000, 10）为什么慢？如何优化？

**Q:** 深分页为什么慢？有哪些优化方法？

**A:**

深分页慢是因为 MySQL 需要扫描并丢弃大量前置记录，offset 越大越慢。

**优化方案：**
1. **延迟关联**：先通过索引仅查询主键 ID，再关联原表查询所需字段，避免回表开销；
2. **书签 / 游标分页**：用上一页最后记录的 ID（或排序字段值）作为条件，直接向后定位，避免 offset 扫描，例如 `WHERE id > 1000000 LIMIT 10`。

## 操作系统高频问答整理

### 1. 为什么进程切换比线程切换更加耗时？

**Q:** 进程切换开销为什么比线程切换大？

**A:**

因为进程切换需要进行虚拟地址切换，虚拟地址空间切换耗时的核心原因，是**页表切换导致 TLB 失效**，进而引发内存访问性能骤降：

切换虚拟地址空间本质上是切换页表（修改 CR3 寄存器），会导致 CPU 中缓存虚拟地址映射的 TLB 全部失效。
TLB 失效后，每次内存访问都需要走多级页表查询，多次访问内存，延迟大幅升高。
同时，虚拟地址索引的 CPU 缓存也会出现大量不命中，需要额外开销维护一致性，进一步拖慢性能。

相比之下，线程切换共享同一虚拟地址空间，无需切换页表，也不会触发 TLB 失效，因此开销远低于进程切换。

### 2. 分页 vs 分段（面试速记版）

**Q:** 分页和分段区别是什么？为什么现代操作系统大多采用段页式？

**A:**

**核心定义：**
- **分页**：物理 / 逻辑地址均划分为固定大小的页（Page）。由系统强制划分，对程序透明。
- **分段**：逻辑地址划分为大小不等的段（Segment）。按程序逻辑结构划分（如代码段、数据段），对程序可见。

**为什么现代操作系统大多采用「段页式」存储管理？**

段页式存储，是把分段和分页结合起来的内存管理方案，核心目的是**同时兼顾两者的优点，解决单一方案的缺陷：**

- **继承分段的优势**：贴合程序逻辑，便于管理与保护
  分段按程序的逻辑结构（代码段、数据段、栈段）划分，天然支持：
  - 按段设置独立的访问权限（代码段只读、数据段可读写），安全性更高
  - 段的大小可按需扩展，无需修改页表，适配性更好

- **继承分页的优势**：高效利用物理内存，解决碎片问题
  分页把每个段再拆成固定大小的页，解决了分段的致命缺陷：
  - 页可以离散映射到物理内存，彻底消除外部碎片
  - 支持虚拟内存、按需调页，实现进程间的内存共享与交换

**实现方式：二级地址转换**
逻辑地址先按段号查段表，找到该段的页表基址；再按页号查页表，最终得到物理地址。

**TLB 的影响**：段页式的二级查表会增加地址转换开销，但现代 CPU 的 TLB（快表）可以缓存段 + 页的映射结果，大幅降低转换延迟。

### 3. 进程页表里，页在内存和页已换出的映射都存在吗？物理页号和 swap 地址又存在哪里？

**Q:** 换出的页在页表中还占位置吗？

**A:**

是的，进程页表里会同时存在这两种映射，它们都存放在**同一个页表项（PTE）**中，通过 **Present 位**区分状态：
- **Present=1**（页在内存）：PTE 存物理页号，由 MMU 硬件直接解析，完成地址转换；
- **Present=0**（页已换出）：PTE 存 swap 分区 + 偏移量，由操作系统内核解析，触发缺页中断后处理。

### 4. 内存映射（mmap）和普通 read 系统调用有什么区别？为什么 read 要两次拷贝？

**Q:** mmap 和 read 区别是什么？为什么 mmap 更少拷贝？

**A:**

核心区别在于数据拷贝路径：
- 普通 read 需要**两次拷贝**：第一次是磁盘数据读到内核页缓存，第二次是从内核页缓存拷贝到用户态缓冲区，开销更大。
- mmap 内存映射只需要**一次拷贝**：首先内核会通过磁盘IO将文件读到内核页缓存，然后mmap将虚拟地址空间和内核页缓存地址做映射，这样就可以直接访问了，无需再将内容read进自定义用户缓冲区，减少一次拷贝

- 场景区分：
- 普通 read：适合流式顺序读、小文件、日志追加、只读取文件局部数据的场景。
- mmap：适合大文件随机访问、数据库页管理、进程共享内存、直接指针操作文件的场景。

## C++ 基础高频问答整理

### 5. C++ 中有哪些同步与互斥机制？各自作用是什么？

**Q:** C++ 标准库提供了哪些线程同步机制？互斥和同步有什么区别？

**A:**

**核心概念区分：**
- **互斥**：防止多个线程同时访问共享资源，解决"竞态条件"问题
- **同步**：控制多个线程之间的执行顺序，让一个线程等待另一个线程完成某个工作再继续

### 互斥机制（防止同时访问）：

| 机制 | 作用 | 适用场景 |
|------|------|----------|
| `std::mutex` | 基础互斥锁，最常用的互斥原语 | 保护共享资源，同一时间只有一个线程能持有锁 |
| `std::lock_guard<mutex>` | RAII 风格自动锁，构造加锁析构解锁 | **日常推荐**，不用手动 unlock，异常安全 |
| `std::unique_lock<mutex>` | 更灵活的锁，支持延迟加锁、提前解锁、移动 | 需要和条件变量配合使用，或者需要更灵活控制锁的时候用 |
| `std::recursive_mutex` | 递归锁，同一个线程可以多次加锁不会死锁 | 递归函数需要加锁的场景，避免自己锁死自己 |
| `std::atomic<T>` | 原子变量，无锁并发编程 | 简单的计数器、状态标志，性能比加锁高很多，不需要互斥锁就能保证线程安全 |

### 同步机制（控制执行顺序）：

| 机制 | 作用 | 适用场景 |
|------|------|----------|
| `std::condition_variable` | 条件变量，等待/唤醒机制 | 生产者消费者模型，当缓冲区满/空时，生产者/消费者等待，被唤醒后继续干活 |
| `std::future<T>` / `std::promise<T>` | 异步结果同步，一个线程等待另一个线程的结果 | 异步任务，主线程等待异步线程计算完成拿到结果 |
| `std::barrier` (C++20) | 多线程同步卡点，所有线程到达卡点后才能继续 | 并行计算，多个线程都完成自己的工作后，才能进入下一步 |
| `std::latch` / `std::countdown_latch` | 倒计时锁，等待 N 个任务完成再继续 | 主线程等待多个 worker 线程都干完活，再汇总结果 |

**一句话总结：** 互斥保护共享资源不被并发访问，同步保证执行顺序，二者配合才能写出正确的多线程程序。

### 6. C++ 中如何实现 SSL/TLS 加密通信？

**Q:** C++ 要做 HTTPS 加密通信，怎么实现 SSL/TLS？

**A:**

C++ 标准库没有内置 SSL/TLS 功能，**通常使用 OpenSSL 库** 来实现加密通信，也可以使用 Boost.ASNL、MbedTLS 等第三方库，OpenSSL 是最主流的选择。

**完整流程：**

1. **初始化 OpenSSL 库**：
   - `SSL_library_init()` 加载所有加密算法
   - `SSL_CTX_new()` 创建 SSL 上下文，指定协议版本（TLS 1.2/1.3）

2. **建立 TCP 连接**：先正常建立 TCP 连接，SSL 是在 TCP 之上的加密层。

3. **SSL 握手：**
   - 创建 `SSL` 对象，绑定 TCP socket
   - 调用 `SSL_connect()`（客户端）或 `SSL_accept()`（服务端）完成握手
   - 握手过程中：交换版本、加密套件、证书，协商密钥，完成身份验证

4. **证书验证：**
   - **客户端**：验证服务端证书是否合法（是否由可信 CA 签发、域名是否匹配、是否过期）
   - **服务端**：如果需要双向认证，也会验证客户端证书

5. **加密通信：**
   - 握手成功后，使用 `SSL_write()` 发送加密数据，`SSL_read()` 读取解密数据
   - OpenSSL 底层自动处理加密解密，开发者不用关心具体加密算法

6. **关闭连接：**
   - `SSL_shutdown()` 关闭 SSL 连接
   - `SSL_free()` 释放 SSL 对象
   - `SSL_CTX_free()` 释放上下文

**证书配置要点：**
- 服务端：需要配置自己的**证书文件（.crt/.pem）**和**私钥文件（.key）**
- 客户端：需要加载可信 CA 证书，用来验证服务端证书

**一句话：** TCP 连接建好后，用 OpenSSL 做 SSL 握手，握手成功后用 SSL_read/SSL_write 加密收发数据。

### 7. 什么是 RESTful API？如何在 C++ 中构建 RESTful API？

**Q:** RESTful API 设计原则是什么？C++ 怎么写 RESTful 接口？

**A:**

**RESTful API** 是一种**基于 HTTP 协议的 Web API 设计风格**，核心设计原则：
- **资源导向**：万物皆是资源，URL 定位资源，用名词表示资源（如 `/users/{id}`）
- **HTTP 方法语义化**：用不同 HTTP 方法表示对资源的不同操作：
  - `GET` → 获取资源
  - `POST` → 创建资源
  - `PUT` → 更新资源
  - `DELETE` → 删除资源
- **无状态**：每个请求独立，服务端不存储客户端状态，依靠请求本身包含所有信息
- **JSON 传输**：请求和响应通常用 JSON 格式传输数据

**C++ 构建 RESTful API：**
C++ 没有标准库实现，常用第三方 HTTP 框架：`libhv`、`Poco`、`Crow`、`Boost.Beast` 等。

**libhv 示例代码：**
```cpp
#include "hv/HttpServer.h"
using namespace hv;

int main() {
    HttpService router;

    // GET 接口，3 行搞定
    router.GET("/", [](auto* req, auto* res) {
        res->json = {{"code", 200}, {"msg", "hello libhv"}};
    });

    // 启动服务
    HttpServer server;
    server.registerHttpService(&router);
    server.listen(8000);
    server.start();

    while(1) hv_sleep(1);
    return 0;
}
```

**libhv 特点：** 简单易用，文档齐全，性能不错，路由注册优雅，天生支持 JSON，开发 RESTful API 非常高效，真正做到"3 行一个接口"。

### 8. 什么是反向代理？核心作用是什么？C++ 中怎么用？

**Q:** 反向代理是什么？主要解决什么问题？

**A:**

**一句话定义：** 反向代理 = 站在**后端服务前面**的"中间人"。客户端只访问代理服务器，代理把请求转发给真正的后端服务，再把结果返回给客户端。客户端**不知道**真正的服务器是谁、有多少台。

**核心作用（必背）：**

| 作用 | 说明 |
|------|------|
| **隐藏后端服务** | 外部只能看到代理 IP，看不到真实服务器 IP，提高安全性 |
| **负载均衡** | 把流量均匀分给多台后端服务，防止单台被压垮 |
| **高可用 & 故障转移** | 某台后端挂了，代理自动把流量切到健康机器，整体服务可用 |
| **请求过滤 & 限流 & 防攻击** | 防 DDoS、防爬虫、黑白名单、流量限制，保护后端 |
| **协议转换 & HTTPS 卸载** | 统一做 HTTPS 加解密，后端只用跑 HTTP；支持 HTTP → gRPC 等协议转换 |
| **缓存静态资源** | 静态文件（CSS/JS/图片）直接由代理返回，减轻后端压力 |

**C++ 中怎么使用反向代理：**
- 生产环境一般不用自己写，直接用成熟开源：**Nginx** 是最常用的反向代理，配置简单，性能极高
- 如果要自己在 C++ 程序中实现反向代理，可以用 `libhv`、`Boost.Beast` 等 HTTP 库，自己转发请求；适合嵌入式场景或定制需求

**正向代理 vs 反向代理区别：**
- **正向代理**：代理**客户端**，帮客户端访问外网（比如 VPN），客户端知道目标服务器
- **反向代理**：代理**服务端**，帮服务端收请求，客户端不知道真实服务器

## Raft 算法高频问答整理

### 1. 投票规则是什么？什么情况下会给对方投票？

**Q:** Candidate 来请求投票，Follower 什么情况会投它？什么情况会拒绝？

**A:**

完整投票规则判断流程：

| 情况 | 投票决策 |
|------|----------|
| Candidate 的任期 < 当前节点任期 | 拒绝，Candidate 过期了 |
| Candidate 的任期 > 当前节点任期 | 接受，更新自己任期，转变为 Follower，投给它 |
| 任期相等 | 如果这一轮我还没投过票，**且 Candidate 日志至少和我一样新** → 投票；已经投过票 / 日志没我新 → 拒绝 |

**为什么要求 "Candidate 日志至少和我一样新"：**
这是为了保证**领导人完全性**，最终选出的 Leader 一定包含了所有已经提交的日志，不会丢掉已经提交的数据。如果 Candidate 日志不全，说明它跟不上最新进度，不能当 Leader。

怎么判断谁日志更新：先比最后一条日志的**任期号**，任期大就是更新；任期相同比**日志索引**，索引大就是更新。

---

### 2. 日志追加的时候，为什么会prevlog的匹配点不是follower的最后一条？常见原因是什么？
两种常见原因：

**1. Follower 存有 "无效日志"**：
原 leader 宕机后，集群先选了个日志不全的 "临时 leader"（它是剩下节点中日志最多的），还往 follower 里写了几条新日志。写完后日志总长度依旧少于原 leader，等原 leader 恢复后重新当选，由于任期比临时leader小，他就会降级为follower，然后等待临时leader的心跳包发送过来和自己同步日志，他们会一直协调找到相同的prevlog位置（当然不是本地日志的最后一条），然后旧leader旧会从该位置开始截断自己往后的所有未同步的无效的日志，来逐渐和新leader保持同步。

**2. 网络丢包导致 nextIndex 没更新**：
如果 follower 在处理日志追加过程中，已经成功写入一部分 leader 发来的新日志，但由于网络原因，follower 的成功回复消息没能到达 leader，导致 leader 的 nextIndex 没有更新。所以下一次发送日志给该 follower 时，匹配到的位置就不是最后一条，需要往前找。


---
### 3. Raft 从设计上就不保证「单机独存的未提交日志」不丢失，本来就默认这类日志可以作废，那业务怎么解决？不能随便丢业务数据啊。
- 业务写请求，必须等 Raft 日志提交成功（多数派复制 + commit） 再给客户端返回成功。没提交成功，客户端就认为写入失败，可以重试，就算旧 Leader 宕机重启日志被清，业务层面本来就不认这条写入，无数据丢失
- 如果只是把日志提交到了leader本地的日志队列就返回成功的话，那可能会导致业务数据丢失。因为单机写入后未同步就宕机可能会导致你认为做效的业务数据丢失。

- 旧 Leader 单机独存、未同步多数派的未提交日志，确实会被新 Leader 截断丢弃，这是 Raft 设计允许的；Raft 只保证已提交（多数派复制）日志永不丢失，业务上通过等待集群提交成功再响应客户端，来避免业务数据丢失。
